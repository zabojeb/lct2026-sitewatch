# СтройКонтур

Рабочая демонстрация мультикамерного контроля стройплощадки. Интерфейс использует не нарисованные предикты, а исходные YOLO-аннотации из двух наборов данных:

- `nickpudovkin/const-video-v2i-yolo26`: 1 407 кадров, 18 классов, несколько камер в течение одного дня;
- `nickpudovkin/dataset-object-identication-training-construction`: 1 046 кадров долгосрочного наблюдения стройки.

## Что реализовано

- реальные рамки объектов из исходных YOLO-аннотаций; недобор и отсутствие обязательной техники показываются красным, лишняя техника, простой и неверная зона — жёлтым;
- пять камер и синхронные серии кадров; одинаковая перемотка на главном экране и карте;
- один вероятный этап для всей площадки: техника объединяется из синхронного среза всех доступных камер, а выбранная камера влияет только на показываемые bbox и локальные зональные события;
- сравнение количества техники в выбранном кадре с редактируемым профилем текущего этапа;
- ссылка из нарушения зоны сразу открывает ту же камеру и тот же кадр на карте;
- определение текущего этапа по профилям `required / required_any / optional`, количествам и мере сходства;
- ручной выбор принятого текущего этапа;
- календарный план как редактируемая последовательность этапов: добавление, удаление, перетаскивание, изменение длительности и автоматический пересчёт полных дат;
- расчёт отставания по границам плановых этапов, фактическому началу и длительности наблюдаемого системой этапа;
- сравнение «план / наблюдения» по общей шкале времени;
- отдельные интервалы причин отклонений: недобор, отсутствие обязательной техники, простой и работа не в той зоне; возможная причина раскрывается при наведении;
- фактическая строка шкалы показывает только проверяемые даты и количество исходных кадров;
- трекинг техники внутри камеры с постоянным ID;
- подтверждение неподвижности по длительности непрерывного трека, нормированному смещению bbox и изменению пикселей внутри рамки;
- SIFT-сопоставление ключевых точек, RANSAC-гомография и перенос bbox двух камер в общую локальную плоскость;
- карта запретных зон поверх кадра выбранной камеры;
- многоугольные зоны: перенос фигуры, перенос вершин, добавление вершины на ребро и обвод новой зоны;
- для одного полигона можно выбрать несколько запрещённых классов техники; изменение правила сразу пересчитывает алерты и цвет bbox;
- для каждого полигона на выбранном кадре рассчитывается процент читаемой видимости: изображение дискретизируется внутри границы, засвеченные и проваленные в чёрное точки исключаются;
- редактирование названий зон прямо в боковой панели;
- локальный прогон `SmolVLM-256M-Instruct` по всем 22 демонстрационным кадрам с bbox; его результат используется только как семантический контекст, а не как источник алерта;
- операционное заключение `VLM + аналитика`: плановый и наблюдаемый этапы, подтверждающие классы техники, нарушения и возможные причины потери темпа объединяются в один динамический вывод без служебных кодов модели;
- через колокольчик можно загрузить проектный вид итогового здания; интерфейс сравнивает его с текущим кадром, объединяет структурное сходство, фактический этап и контекст VLM и показывает процент визуальной готовности с уровнем уверенности;
- история из 11 контрольных кадров с тремя распознанными этапами; для двух ранних этапов поверх реальных фонов сгенерированы и точно размечены прозрачные изображения техники;
- колокольчик с задачами первичной настройки: для каждой камеры без правил сотруднику предлагается выбрать технику, назвать запретную область и обвести её многоугольником;
- экспорт JSON со всеми основаниями вывода;
- прогрессивная загрузка кадров: сначала показывается локальное лёгкое превью, затем без чёрного экрана проявляется полный снимок; остальные кадры выбранной камеры догружаются в фоне.

## Сборка данных

```bash
python3 -m venv .venv
.venv/bin/pip install -r scripts/requirements.txt
.venv/bin/python scripts/build_real_demo.py \
  --video-root /path/to/const_video.v2i.yolo26 \
  --progress-root /path/to/Dataset-Object-identication-training-construction \
  --out dist
```

Скрипт:

1. читает bbox напрямую из YOLO-файлов;
2. строит локальные треки по классу, IoU и расстоянию нижнего центра bbox;
3. рассчитывает движение относительно диагонали bbox и изменение изображения внутри рамки;
4. сопоставляет кадры SIFT-дескрипторами и отбрасывает выбросы RANSAC;
5. вычисляет межкамерную гомографию и проецирует нижний центр bbox в координаты опорного ракурса;
6. сохраняет оптимизированные WebP и `dist/data/real-session.json`.

Дополнительную демонстрационную историю этапов собирает:

```bash
python3 scripts/build_synthetic_timeline.py
```

Он накладывает PNG техники с прозрачным фоном на реальные кадры площадки, сохраняет точный bbox каждого наложенного объекта и добавляет 11 контрольных наблюдений в `stageTimeline`. Алгоритм распознавания этапа получает только количества классов и bbox — названия этапов в кадры не зашиты.

## Как определяется простой

Одинаковый bbox в двух кадрах сам по себе не считается простоем. Для каждого непрерывного `track_id` используются два независимых признака:

```text
movement = distance(foot_t, foot_t-1) / bbox_diagonal / dt
visual_change = mean(abs(crop_t - crop_t-1)) / 255
```

Берётся медиана окна. Событие появляется только после 60 секунд подряд, когда нормированное перемещение меньше `0.012`, а изменение пикселей внутри объекта меньше `0.022`. Потеря трека более чем на четыре секунды сбрасывает накопленное доказательство. В рабочем потоке порог длительности задаётся профилем техники и обычно должен быть больше демонстрационной минуты.

Так различаются:

- перемещается — меняется нижний центр bbox;
- работает на месте — bbox стабилен, но внутри рамки есть визуальная активность;
- вероятный простой — оба сигнала стабильно малы;
- недостаточно данных — окно короткое или трек прервался.

## Как получаются координаты

Текущая демонстрация действительно вычисляет координаты, но это координаты общей локальной плоскости, а не широта/долгота и не метры генплана.

1. SIFT находит одинаковые устойчивые детали площадки в двух ракурсах.
2. Lowe ratio test удаляет неоднозначные совпадения.
3. RANSAC оценивает гомографию и отбрасывает геометрические выбросы.
4. Нижний центр bbox переносится в систему опорного кадра камеры 8.
5. На этой плоскости выполняются объединение наблюдений и проверка попадания в полигон зоны.

Для данной пары кадров получено 50 геометрически согласованных точек из 66 совпадений, доля согласованных точек 75,8%, RMSE 0,24 px. Это реальные результаты расчёта пайплайна.

Чтобы получить координаты в метрах или на генплане, нужна ещё одна привязка локальной плоскости: минимум четыре неколлинеарные точки с известными координатами либо известные позы камер и параметры объективов. Одних GPS-координат камер недостаточно: нужны также высота, направление, наклон, фокусное расстояние и дисторсия; либо точки соответствия на плане. После этого применяется дополнительная гомография `local → site`, а алгоритм трекинга не меняется.

## Как определяется этап

Для этапа задаются:

- `required` — обязательные классы и минимальные количества;
- `required_any` — достаточно хотя бы одного класса из группы;
- `optional` — допустимая техника, усиливающая совпадение, но не обязательная.

Итоговый балл учитывает долю найденного обязательного количества, необязательные классы, точность состава и штраф за технику вне профиля. Для этапов с количественными нормативами добавляется небольшой вес специфичности набора:

```text
required:
0.67 × покрытие обязательного количества
+ 0.10 × покрытие optional
+ 0.08 × точность состава
- 0.35 × доля техники вне профиля
+ до 0.08 × специфичность количественного набора

required_any:
0.65 × наличие класса из группы
+ 0.20 × покрытие optional
+ 0.15 × точность состава
- 0.45 × доля техники вне профиля
```

Штраф за технику вне профиля не позволяет одному специфичному объекту перевесить весь состав площадки. Оператор видит единую оценку всех камер и может подтвердить другой фактический этап вручную. Плановый этап при этом всегда берётся из календаря и не подменяется ручным выбором.

### Объединение нескольких камер

Сначала формируется временной срез одного объекта: по одному ближайшему кадру каждой камеры в допустимом окне времени. Этап не рассчитывается отдельно для ракурсов.

- Если у камер есть координаты общей плоскости, нижние центры bbox одного класса объединяются по расстоянию функцией `fuseCameraDetections`; одна машина, видимая с двух сторон, считается один раз.
- Если общая калибровка конкретных камер ещё не выполнена, используется консервативная нижняя оценка — максимум количества класса среди камер, а не сумма. Это не создаёт ложный парк техники из повторных ракурсов.
- Отсутствие обязательной техники и соответствие этапу проверяются по объединённому составу площадки. Лишняя техника, простой и въезд в запретную зону дополнительно подсвечиваются на том кадре, где они видны.

Аудит 100 изображений организаторов подтвердил, что отдельные снимки показывают разные части и параллельные процессы: земляные работы, устройство свай и крановые операции могут быть видны в разных ракурсах. Сами 100 изображений относятся к разным датам и объектам, поэтому они не складываются в один временной срез.

## Запретные зоны и VLM

В версии 18 система не выдаёт вручную придуманные рабочие зоны за результат алгоритма. Единственный стартовый полигон для камеры 9 — демонстрационный пример правила. Для остальных камер в колокольчике создаются задачи первичной настройки. Сотрудник:

1. выбирает камеру;
2. задаёт понятное название области;
3. выбирает один или несколько типов техники, которым въезд запрещён;
4. обводит многоугольник прямо по кадру.

После сохранения можно менять список запрещённых классов, двигать весь полигон, отдельные вершины и разбивать ребро кнопкой `+`. Правило пересчитывается сразу. Техника попадает в запретную область, когда нижний центр её bbox — условная точка контакта с землёй — оказывается внутри многоугольника. Остальные классы техники этим полигоном не ограничиваются.

`SmolVLM-256M-Instruct` запускается на кадре с bbox и классифицирует общий контекст (`основной фронт работ`, `проезд`, `складирование`, `сектор кранов`). В интерфейсе этот контекст объединяется с проверяемыми правилами: календарным этапом, составом техники, простоем и попаданием в запретный полигон. VLM помогает интерпретировать сцену, но не создаёт координаты полигона и не выпускает алерт без подтверждённого геометрического правила.

Полностью автоматическое предложение границы можно добавить отдельной моделью сегментации/grounded segmentation и оставить сотруднику подтверждение. Одна VLM, отвечающая текстом, недостаточно надёжна для точной границы и производственного алерта.

В текущем прототипе видимость конкретной зоны рассчитывается честно в координатах выбранной камеры: пиксели внутри многоугольника переводятся в равномерную сетку, а засвеченные и проваленные в чёрное точки считаются нечитаемыми. Результат пересчитывается при смене кадра или геометрии полигона. Для межкамерной видимости на генплане следующим уровнем остаётся проекция полей зрения всех камер в общую метрическую систему координат.

## Оценка визуальной готовности

Оператор загружает проектную визуализацию через колокольчик или карточку «Готовность по проекту». Изображение уменьшается до безопасного размера и хранится локально в браузере. Для текущего кадра и проекта строится сеточный дескриптор яркости и границ; далее оценка объединяет:

- структурное сходство текущего и проектного видов — 55%;
- положение подтверждённого этапа в календарной последовательности — 30%;
- контекст локального `SmolVLM` — 15%.

Вместе с процентом выводится уверенность, зависящая от сходства ракурсов. Это предварительная визуальная оценка, а не приёмка объёмов: для производственного процента готовности нужны BIM-элементы, одинаковые камеры и поэлементное сопоставление конструкций.

## Ограничения

- долгосрочные контрольные кадры не используются для вывода о простое: неподвижность подтверждается только внутри непрерывной короткой серии;
- изменения запретных зон пока живут в состоянии браузера;
- `SmolVLM-256M-Instruct` используется как лёгкий семантический классификатор; для автоматической сегментации зон нужен отдельный сегментационный модуль или готовая BIM/генплан-разметка;
- загруженный проектный вид даёт предварительную визуальную готовность, но не заменяет поэлементную BIM-проверку объёмов;
- метры и координаты генплана появятся после добавления геодезических опорных точек или полной калибровки камер.
